
# Описание архитектуры и структуры проекта: Чат-сервер (Версия 4)

## 1. Обзор проекта

Серверная часть представляет собой асинхронное, многопользовательское ядро для чат-приложения, разработанное на C++ с использованием `QCoreApplication`. Он спроектирован для одновременной обработки подключений от множества клиентов, аутентификации пользователей, обработки и хранения сообщений, а также управления списками контактов и статусами присутствия.

### Ключевые технологии и парадигмы:

-   **Язык:** C++
-   **Фреймворк:** Qt 6 (без GUI-компонентов).
-   **Сетевое взаимодействие:**
    -   **TCP/IP (`QTcpServer`):** Для нативных десктопных клиентов (как ваш).
    -   **WebSockets (`QWebSocketServer`):** Для потенциальных веб-клиентов, что делает архитектуру гибкой и готовой к расширению.
-   **База данных:** **SQLite (`QSqlDatabase`)** для хранения всех персистентных данных (пользователи, сообщения, контакты).
-   **Архитектурные паттерны:**
    -   **Событийно-ориентированная модель:** Сервер построен вокруг асинхронной обработки событий Qt (новое подключение, получение данных, дисконнект).
    -   **Команда (Command Pattern):** Реализован через `QMap` с указателями на методы-обработчики, что обеспечивает слабую связанность и легкую расширяемость.

## 2. Ключевые архитектурные решения

### 2.1. Гибридный сетевой уровень (TCP + WebSocket)

Сервер одновременно слушает два разных порта для двух протоколов, что является мощным решением для кросс-платформенности.
-   `QTcpServer` принимает подключения от нативного Qt-клиента. Он использует `QDataStream` для разбора бинарного потока, где каждое сообщение предваряется его размером (`quint32`).
-   `QWebSocketServer` принимает подключения от клиентов, поддерживающих WebSockets (например, браузеры). Он работает с текстовыми сообщениями в формате JSON.
-   **Унификация:** Важно, что после получения и парсинга данных оба типа подключений передают `QJsonObject` в единый метод `processJsonRequest`. Это предотвращает дублирование кода и позволяет всей бизнес-логике быть независимой от транспортного протокола.

### 2.2. Обработка команд на основе карты обработчиков (Handler Map)

Это ядро бизнес-логики сервера. Вместо громоздкой конструкции `if-else` или `switch` для разбора типов запросов, используется элегантный и масштабируемый подход.
-   **Структура:** В классе `Server` есть поле `QMap<QString, Handler> m_handlers`, где `Handler` — это `using Handler = void (Server::*)(QObject*, const QJsonObject&)`.
-   **Инициализация:** В методе `initHandlers()` эта карта заполняется. Ключом является строковое имя команды (например, `"login"`, `"private_message"`), а значением — указатель на метод, который должен обработать эту команду (`&Server::handleLogin`, `&Server::handlePrivateMessage`).
-   **Исполнение:** Метод `processJsonRequest` извлекает поле `"type"` из входящего JSON, находит соответствующий указатель на метод в `m_handlers` и вызывает его, передавая сокет клиента и сам JSON-объект.

### 2.3. Управление состоянием клиентов

Сервер должен в реальном времени знать, какие пользователи онлайн и через какой сокет с ними можно связаться. Для этого используется двойное отображение:

-   `QMap<QString, QObject*> m_clients;` (Имя пользователя -> Указатель на сокет)
    -   **Назначение:** Быстрый поиск сокета по имени пользователя. Необходимо, когда нужно отправить сообщение конкретному получателю (например, в `handlePrivateMessage` или `handleTyping`).

-   `QMap<QObject*, QString> m_clientsReverse;` (Указатель на сокет -> Имя пользователя)
    -   **Назначение:** Быстрое определение аутентифицированного пользователя по сокету, с которого пришел запрос. Это используется практически в каждом обработчике для идентификации отправителя.

Эта связка обеспечивает быстрый доступ O(log n) в обе стороны и является центральным элементом управления онлайн-пользователями.

### 2.4. Слой персистентности (База данных SQLite)

Все данные, которые должны пережить перезапуск сервера, хранятся в файловой базе данных SQLite.

-   **Инициализация:** Метод `initDatabase()` при старте сервера создает файл `messenger.db` (если он не существует) и определяет в нем три основные таблицы:
    1.  **`users`**: Хранит информацию о пользователях (логин, хэш пароля, отображаемое имя, дата последнего визита и т.д.).
    2.  **`messages`**: Основная таблица, хранящая все сообщения. В ней есть поля `fromUser`, `toUser`, текст (`payload`), временная метка, статусы (`is_delivered`, `is_read`), а также `reply_to_id` для связи ответов.
    3.  **`contacts`**: Таблица-связка для управления отношениями между пользователями. Хранит пары ID пользователей и их статус (`0` — запрос отправлен, `1` — подтвержден).

-   **Взаимодействие:** Каждый метод-обработчик использует `QSqlQuery` для выполнения запросов к этой базе данных (`INSERT`, `SELECT`, `UPDATE`, `DELETE`).

## 3. Компонентный разбор и жизненный цикл запроса

Рассмотрим типичный сценарий: **отправка личного сообщения**.

1.  **Получение данных (Сетевой слой):**
    -   Клиент отправляет бинарные данные.
    -   `onTcpReadyRead()` срабатывает на сервере.
    -   С помощью `QDataStream` и `m_nextBlockSizes` извлекается полный JSON-пакет.
    -   `QJsonObject` передается в `processJsonRequest()`.

2.  **Маршрутизация (Обработчик запросов):**
    -   `processJsonRequest()` читает `"type": "private_message"`.
    -   В `m_handlers` находится соответствующий указатель на `&Server::handlePrivateMessage`.
    -   Вызывается `handlePrivateMessage(socket, request)`.

3.  **Обработка (Бизнес-логика):**
    -   **Аутентификация:** `handlePrivateMessage` первым делом проверяет, что `fromUser` в запросе совпадает с именем пользователя, ассоциированным с этим сокетом в `m_clientsReverse`. Это простая, но важная мера безопасности.
    -   **Сохранение в БД:** Создается `QSqlQuery` для `INSERT` нового сообщения в таблицу `messages`. Все данные из JSON (отправитель, получатель, текст, `reply_to_id`) записываются в базу. Сервер получает `messageId` через `query.lastInsertId()`.
    -   **Echo-ответ отправителю:** Сервер формирует "echo"-сообщение. Это копия исходного сообщения, но дополненная серверными данными: `id` из базы данных и `timestamp`. Наличие `temp_id` из клиентского запроса позволяет клиенту сопоставить отправляемое сообщение с подтвержденным.
    -   **Доставка получателю:**
        -   Сервер ищет получателя (`toUser`) в `m_clients`.
        -   **Если получатель онлайн:** Сообщение (уже без `temp_id`) отправляется на его сокет.
        -   **Если получатель офлайн:** Ничего не происходит. Сообщение просто лежит в базе данных со статусом `is_delivered = 0`. В будущем может быть реализована логика доставки офлайн-сообщений при входе пользователя.

4.  **Оповещение и обновление состояния:**
    -   При подключении и отключении клиента (`onNew...Connection`, `onClientDisconnected`) вызывается `broadcastUserList()`, который рассылает всем онлайн-пользователям актуальный список тех, кто сейчас в сети.

## 4. Итоги по архитектуре

Сервер V4 представляет собой хорошо спроектированную, надежную и эффективную систему.

-   **Сильные стороны:**
    -   **Гибкость:** Поддержка TCP и WebSockets открывает двери для разных типов клиентов.
    -   **Масштабируемость:** Паттерн "Handler Map" позволяет легко добавлять новые функции, просто написав новый метод и добавив одну строчку в `initHandlers`.
    -   **Производительность:** Использование `QMap` для управления клиентами и асинхронная природа Qt обеспечивают быструю обработку запросов без блокировок.
    -   **Надежность:** Хранение всех данных в SQLite гарантирует их сохранность между сессиями.
-   **Потенциальные зоны для роста:**
    -   **Безопасность:** Текущая система аутентификации базовая. Можно добавить токены сессий вместо простого хранения связки "юзер-сокет".
    -   **Масштабирование:** Для высоконагруженного сервиса SQLite может стать узким местом; в будущем его можно заменить на более мощную СУБД (например, PostgreSQL).
    -   **Отказоустойчивость:** Сервер является единой точкой отказа. В будущем можно рассмотреть архитектуру с балансировщиком нагрузки и несколькими инстансами сервера.
